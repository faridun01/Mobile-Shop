# Диагностика экрана «Произошла ошибка», 17.10.2026

Исправления не вносились. Исходный клиентский случай не воспроизведён: скриншот передан клиентом, страница, действие, версия и журнал ошибки неизвестны. Ниже перечислены найденные механизмы, а не установленная причина конкретного скриншота.

## 1. Нарушение порядка React-хуков — воспроизведено в изолированном рендере

- `src/components/common/DailyRateModal.tsx:18`: возврат при отсутствии `currentUser` расположен перед `useState`, `useRef`, `useEffect`.
- `src/components/pages/RevisionPage.tsx:68`: возврат для пользователя без ADMIN расположен перед `useMemo`, `useState` и другими хуками.

Если один экземпляр компонента проходит переход «пользователь отсутствует → присутствует» или «не ADMIN → ADMIN», количество хуков меняется. Диагностические тесты существующих компонентов получили `Rendered more hooks than during the previous render`.

Ограничение доказательства: тест искусственно создаёт переход пользователя через mock контекста и повторный render в одном экземпляре. Он подтверждает дефект порядка хуков, но не подтверждает, что production-маршрутизация допускает именно этот переход без перемонтирования. Обычный вход/выход может перемонтировать layout и не проявить дефект. Окно курса подключено к общему `MainLayout`; ревизия имеет дополнительный route-guard ADMIN.

Будущее исправление: вызывать все хуки безусловно до ранних возвратов либо разделить компонент на проверяющую обёртку и дочерний компонент. Добавить тесты переходов с реальным AppProvider/router.

## 2. Отказ загрузки раздела и смена версии — путь ошибки подтверждён, событие на телефоне неизвестно

`src/router/AppRouter.tsx` и `src/router/MainLayout.tsx` используют `React.lazy` для layout, страниц и сканера. Отклонённый Promise импорта становится ошибкой React-рендера. В диагностическом тесте воспроизведено отклонение с `TypeError: Failed to fetch dynamically imported module`.

В проекте нет обработчика `vite:preloadError` и отдельного восстановления неудачной загрузки раздела. Корневой ErrorBoundary показывает общий экран.

Возможные условия: обрыв загрузки JS, недоступный файл, открытая старая вкладка после удаления старых hash-файлов, перехват запросов сетью. Простая ошибка `/api` сама по себе этот механизм не подтверждает.

Дополнительная проблема раздачи: в `server/src/index.ts:21–36` после `express.static` стоит общий SPA fallback. Для отсутствующего `/assets/*.js` он может вернуть `index.html` с HTTP 200. Локальный HTTP-пробник, повторяющий этот порядок middleware и использующий существующий dist, получил:

```json
{"request":"/assets/diagnostic-missing-old-chunk.js","status":200,"contentType":"text/html; charset=UTF-8","htmlInsteadOfJs":true}
```

Это не проверка публичного сервера и не запуск production backend: использован отдельный локальный Express без БД. Такой ответ непригоден как JavaScript-модуль. Конкретное поведение Safari и production-прокси не воспроизводилось.

Конфигурация PWA: `skipWaiting: true`, `clientsClaim: true`, автоматическое обновление. Сервис обновлений откладывает reload при незавершённой работе. Потенциально новая SW может уже контролировать страницу, пока старая страница продолжает работать. Не выполнен эксперимент с двумя production-релизами и реальным service worker, поэтому это гипотеза о дополнительном триггере, не самостоятельная доказанная причина. Нельзя утверждать, что любой деплой ломает открытые клиенты.

Сканер исключён из precache (`globIgnores` в vite.config.ts); его первый запуск требует доступности ресурсов, если они ещё не загружены. Отказ ленивого ScannerModal может попадать в тот же общий экран. Зависимость конкретного скриншота от сканера неизвестна.

Будущее исправление: корректный 404 для отсутствующих assets, политика сохранения старых файлов/согласованного обновления, ограниченное восстановление preload-сбоев с сохранением незавершённых операций. Не применять безусловный reload во время финансового запроса или заполненной корзины.

## 3. Невалидные сохранённые категории расходов — воспроизведено

`src/components/pages/ExpensesPage.tsx:175–181` читает `custom_expense_categories` через `JSON.parse`, проверяя только синтаксис JSON. Значения `null`, `{}` и `123` синтаксически допустимы и проходят try/catch.

На строке 397 выполняется `[...STANDARD_CATEGORIES, ...customCategories]`. Для этих значений возникает TypeError о неитерируемом значении во время рендера. Диагностические тесты воспроизвели все три случая; контрольный `[]` отрисовывает страницу успешно.

Ограничение: текущий обработчик сохранения пишет массив; не найден штатный сценарий, записывающий именно `null` или объект. Неизвестно, есть ли такая запись у клиента. Это подтверждённая уязвимость к неверной форме локальных данных, а не доказанный массовый сбой.

Будущее исправление: Array.isArray и проверка формы элементов перед использованием, безопасное восстановление только соответствующей настройки. Не удалять целиком localStorage: там находится сессия и другие данные.

## 4. Почему точный диагноз клиентского случая сейчас недоступен

`src/components/common/ErrorBoundary.tsx:24–25` пишет error и componentStack только в `console.error`. Не сохраняет диагностическую запись, страницу, версию сборки и идентификатор ошибки для пользователя; серверного сбора этих ошибок не найдено. После обновления страницы сведения могут быть потеряны.

В `src/App.tsx` используется один общий ErrorBoundary, поэтому ошибка отдельной страницы заменяет весь интерфейс. `PWAUpdateNotifier` также находится внутри него и после сбоя демонтируется вместе с остальными детьми: его механизм обновлений не является восстановлением уже упавшего UI.

Будущее исправление: минимальный диагностический отчёт с кодом ошибки, маршрутом, build id, message и componentStack; исключить токены, персональные и финансовые данные. Отдельные границы для страниц/ленивых модулей помогут ограничить область сбоя. Это улучшение диагностики и локализации, а не устранение исходных исключений.

## Выполненные проверки и ограничения

- Диагностические React-тесты: 2 файла, 7/7 прошли. Эти тесты проверяют наличие текущих ошибок через ожидаемое исключение — зелёный результат означает успешное воспроизведение, а не исправление продукта.
- SSR-рендер React с подменённым контекстом; iPhone/WebKit, настоящий браузерный ErrorBoundary и пользовательские данные не запускались.
- Проверка отсутствующего chunk: локальный HTTP, 200 + text/html вместо JS.
- Исходные файлы приложения, настройки, зависимости и БД не менялись. Локальные диагностические файлы и вывод: `output/ui-crash-diagnosis/` (игнорируются Git).
- Не делается вывод, что сбой вызван финансовой операцией, БД, памятью iPhone, конкретным релизом или конкретным пользователем: доказательств нет.

1. Устранить условный порядок хуков; проверить переходы пользователя с настоящими provider/router.

3. Исправить раздачу отсутствующих JS и согласованное восстановление lazy/PWA; воспроизвести обновление между двумя сборками на мобильном браузере.
