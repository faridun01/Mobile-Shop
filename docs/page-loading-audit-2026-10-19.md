# Загрузка страниц Mobile Shop — 19 октября 2026

Обычная загрузка всех реализованных экранов в проверенных условиях проходит без падения React, белого экрана и зависшего индикатора. **Проблемы при сбоях API есть:** на 16 адресах первоначальные данные могут не загрузиться, а пользователь не получает явного сообщения об этом. Поэтому заключение «при загрузке никаких проблем не будет» не подтверждается.

Использовались production web build, Chrome, отдельный API и мигрированные временные схемы БД `mobile_shop_audit:55439`. Рабочая БД не затронута. Код приложения и UI в этой проверке не менялись; добавлены тесты и отчёт.

## Реально выполнено

- 24 адреса: 23 экрана и старый адрес `/finance`, перенаправляющий в `/reports`.
- Admin, Partner, Seller; ширины 360, 768, 1280 px.
- **432 проверки холодного открытия и обновления**: каждый адрес × 3 роли × 3 ширины × 2 способа открытия. HTTP-кеш отключён, Service Worker обходится.
- **24 перехода без перезагрузки документа**, браузерные назад/вперёд.
- **46 сценариев** для администратора на 360 px: задержка каждого GET API на 350 мс и отказ GET с 503 — по 23 экранам.
- **14 проверок** входа без сессии, неизвестного адреса, отозванной сессии, недоступного JS-модуля, офлайна и восстановления после обновления.
- Отслеживались необработанные ошибки JavaScript, HTTP-ошибки при нормальной загрузке, ErrorBoundary, отсутствие содержимого и оставшийся индикатор загрузки.
- Типы новых тестов проверены отдельным запуском TypeScript.

В первом варианте тест ошибочно ожидал доступ продавца к настройкам. `SettingsPage` намеренно перенаправляет SELLER на POS. Ожидание исправлено; все шесть затронутых проверок открытия/обновления на трёх ширинах выполнены повторно и прошли. В исходном `result.json` эти три первоначальные ошибки ожидания сохранены; повтор находится в `focused.json`. Они не являются падением приложения и не скрыты из журнала.

## Обнаруженная проблема — ошибка API выглядит как пустые данные

**Приоритет P1 для экранов денег и склада.** При имитации 503 склад показывает «Устройства не найдены», 0 товаров и $0.00. При этом в fixture товар есть. Данные в БД не исчезли: после восстановления API и обновления страницы они возвращаются.

Без явного сообщения об отказе первоначального GET в этом сценарии остались адреса:

`/`, `/expenses`, `/bonuses`, `/owners`, `/purchase`, `/inventory`, `/stock-thresholds`, `/transfer`, `/revision`, `/suppliers`, `/employees`, `/exchange`, `/audit-log`, `/settings`, `/sale`, `/receipts`.

Это не означает, что все эти страницы показывают одинаковые нулевые показатели: где-то пустеет список, где-то селектор или справочник формы. Общая проблема — пользователь не отличает отсутствие данных от невозможности их получить. Другие экраны также не следует считать полностью устойчивыми ко всем частичным отказам: проверялся конкретный сценарий отказа GET, а не каждый запрос отдельно.

Причина видна в `src/context/AppContext.tsx`: ошибки первоначальных запросов и загрузки модулей перехватываются через `console.error`, а `isInitialLoading` снимается в `finally`. Начальные пустые массивы остаются в состоянии; единого доступного странице признака ошибки загрузки нет. Поэтому экран переходит в обычное пустое состояние. Живой WebSocket также не доказывает, что HTTP API или БД успешно отвечают.

Рекомендуемое исправление: хранить ошибку загрузки данных отдельно от пустого результата, показывать понятное сообщение и безопасное действие «Повторить», не представлять неполученные суммы как подтверждённые нули. Проверять успешность каждого обязательного запроса и восстановление после его отказа. В рамках этой проверки исправление приложения не внесено.

## Восстановление и ограничения

- Если модуль страницы недоступен, появляется понятный экран «Не удалось загрузить раздел»; после восстановления загрузки и обновления страница открывается.
- После перехода в офлайн при открытии нового раздела отображается состояние отсутствия связи/ошибки; после восстановления и обновления раздел работает.
- После отзыва сессии открывается страница входа; неизвестный адрес у администратора ведёт на главную.
- При задержке API на 350 мс необработанных падений или оставшегося индикатора загрузки не обнаружено.
- Автоматическое восстановление каждого списка **без обновления страницы** после частичного отказа API не подтверждено.
- Проверялся Chrome. Safari на iPhone, нативные приложения и поведение установленной PWA при смене версии Service Worker в этот прогон не входят.
- Тестовый набор содержит небольшой объём данных. Этот прогон не подтверждает скорость всех экранов на производственной истории за несколько лет, на слабом телефоне или при ограниченной пропускной способности сети.

Артефакты: `output/page-loading/result.json`, `focused.json`, `recovery.json`, `summary.json`; полный журнал — `output/page-loading-run.log`.

Для повторения: `npm run test:page-loading` с явным DATABASE_URL отдельной БД на 55439 и тестовым JWT_SECRET. Тесты также включены в постоянный `test:project-audit`. Они проверяют отсутствие падений и собирают список скрытых ошибок API; отсутствие сообщения об ошибке выведено отдельной находкой, а не отмечено как успешная обработка сбоя.
