## Проблемы перед запуском

### P1 — Неработающий healthcheck блокирует запуск зависимого nginx

- `docker-compose.prod.yml:37`, `docker-compose.staging.yml:36`, `docker-compose.yml:40`: проверяется `http://localhost:3000/api/health`.
- `server/src/index.ts:31`: приложение слушает только `0.0.0.0`.
- В работающем контейнере `mobile_shop_app` wget разрешает localhost как `[::1]` и получает Connection refused. Тот же запрос к `127.0.0.1` успешен.
- nginx в Compose зависит от `service_healthy`; на чистом запуске это может остановить весь запуск сайта.
- Исправление: использовать `127.0.0.1` во всех healthcheck и проверить чистый запуск Compose. Наблюдение сделано на старом контейнере; соответствующая ошибочная конфигурация сохранена и в текущем коде.

### P1 — Стандартные пароли и небезопасный повторный seed

- `prisma/seed.ts:11–14,46–50`: фиксированные пароли; upsert обновляет пароль существующего пользователя.
- Проверка хешей в локальной БД подтвердила **4 активные учётные записи со стандартными seed-паролями**. Это факт о локальной БД, не утверждение о внешнем production.
- Повторный seed возвращает стандартные пароли даже после ручной смены. Защиты от запуска seed в production нет.
- Исправление: отделить тестовый seed от первоначальной production-инициализации; не обновлять существующие пароли; сменить начальные пароли до открытия доступа. Автоматический entrypoint сам seed не запускает.

### P1 — Неверная граница доверия к IP в API

- `server/src/app.ts:34`: `trust proxy = 1`; ограничение попыток входа использует `req.ip`.
- `nginx/nginx.conf:62–68`: в `/api/` задаётся `X-Real-IP`, но отсутствует установка `X-Forwarded-For`. Настройки соседнего `location /` сюда не наследуются.
- Обычные запросы учитываются по IP прокси; присланный клиентом X-Forwarded-For не перезаписывается этим location, что позволяет подменить IP, используемый приложением. Общий nginx rate limit остаётся, но не заменяет защиту входа.
- Исправление: явно задавать доверенный X-Forwarded-For в API location и согласовать trust proxy с фактической цепочкой внешних прокси. Проверить попытки входа с поддельным заголовком.
- Дополнительно: Map попыток входа не очищает давно неиспользуемые ключи — рост памяти при множестве уникальных логинов.

### P2 — CORS не поддерживает заголовок идемпотентности

- `server/src/app.ts:58` разрешает только Content-Type и Authorization.
- `src/context/AppContext.tsx:1359–1408` умеет отправлять Idempotency-Key при передаче ключа вызывающим кодом.
- Пробный OPTIONS подтвердил: Idempotency-Key в разрешённых заголовках отсутствует.
- Последствие условное: финансовый запрос **с этим заголовком** из другого origin, включая native WebView, будет заблокирован браузером. Same-origin веб-запросы этим не затронуты. Это не утверждение, что каждый текущий экран всегда передаёт ключ.
- Исправление: разрешить заголовок и проверить реальный cross-origin запрос. Отдельно проверить, что интерфейс действительно генерирует и повторно использует ключ для повторной отправки одной операции.

### P2 — Восстановление БД недостаточно защищено от плохого архива

- `scripts/restore-db.sh` удаляет public schema до проверки целостности gzip и успешности восстановления. Повреждённый архив оставит базу пустой/частично восстановленной.
- backup и restore жёстко используют пользователя postgres и БД mobile_shop_db, хотя production Compose позволяет переопределить их.
- Исправление: сначала проверить архив и восстановить его в отдельную БД; параметризовать имя БД/пользователя; провести учение по восстановлению. Расписание, внешняя копия и успешное восстановление в этой проверке не подтверждены.

## Дополнительные риски и условия допуска

- nginx обслуживает HTTP на порту 80. Внешнее завершение TLS может быть настроено вне репозитория, но не проверено. До публикации нужны фактическая проверка HTTPS, перенаправления HTTP и работы камеры/PWA на целевом домене.
- В `vercel.json` API направлен на фиксированный Render backend, а WebSocket по умолчанию идёт на origin фронтенда. Для этого варианта деплоя нужно явно настроить `VITE_WS_URL` на backend и проверить соединение. Docker-развёртывание использует другую схему маршрутизации.
- Миграция `20260925150000_deactivate_main_account` отключает MAIN без переноса остатка. В проверенной локальной БД остатки MAIN равны нулю. Для иной БД перед обновлением требуется проверка и перенос ненулевых остатков проводкой, иначе счёт исчезнет из списка активных.
- Обновление последних статусов неоплаченных расходов требует отдельных сценариев create → pay → edit → cancel, включая конкурентную оплату. Пройденные регрессии не доказывают полное покрытие этого нового пути; специальных unit-тестов с payExpense/UNPAID поиском не найдено.
- Остановка сервера вызывает `server.close()` без ожидания завершения запросов, затем отключает Prisma; WebSocket-соединения явно не закрываются. Нужна проверка завершения активной операции при рестарте.
- npm audit сообщает одну базовую проблему uuid с распространением на exceljs/xcode/Capacitor CLI; 4 записи не означают 4 независимых эксплойта. Нужен разбор достижимости и совместимое обновление, а не автоматический `audit fix --force`.
- Образ собран, но полный запуск нового production Compose, Trivy-скан образа, проверка восстановления, нагрузка, все страницы под всеми ролями, реальная камера и Android/iOS на устройствах не выполнены. Полную готовность этих частей подтвердить нельзя.

## Порядок допуска к production

1. Исправить healthcheck, передачу доверенного IP и production-инициализацию пользователей; сменить стандартные пароли.
2. Исправить CORS для используемых cross-origin финансовых запросов.
3. Проверить backup/restore и остатки отключаемых счетов на копии целевой БД.
4. Поднять свежий Compose на staging с HTTPS; пройти вход под ролями, закупку, перемещение, продажу, возврат, оплату/отмену расходов, отчёты и reconnect WebSocket через браузер.
5. Провести проверку миграции копии production-данных, рестарта и скан образа. После этого повторно принять решение о выпуске.
