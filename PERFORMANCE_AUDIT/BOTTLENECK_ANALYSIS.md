# Анализ узких мест

Источник — замеры из [BASELINE_METRICS.md](BASELINE_METRICS.md), CPU-профиль сервера (`node --cpu-prof`, `data/prof/`) и журнал SQL Postgres (`log_min_duration_statement=0` только для базы `perf_test`).

## Методика и важная оговорка о данных

Первая версия тестовой базы содержала все 3 823 продажи «сегодня». На ней история продаж давала 335 тыс. DOM-узлов и 18 с перехода на телефоне — это **ложное** узкое место: в реальной работе за день ~40 продаж. Шаблон был переразложен по 90 дням (детерминированно, `setseed(0.42)`), после чего все замеры повторены. Все выводы ниже — по реалистичным данным.

## Что проверено и узким местом не является

- Старт сервера 745 мс, память 122 МБ в простое — норма для `tsx` + Prisma.
- Мелкие справочные эндпоинты: 4–16 мс.
- Первая загрузка: 18 запросов, 554 КБ по сети без сжатия на тестовом сервере. В проде nginx отдаёт gzip, а хешированные ассеты кэшируются как immutable.
- `react-router` в сборке выглядит как «development build» по строкам предупреждений, но `dist/production` у пакета идентичен (те же 372 КБ, те же строки) — не проблема.
- Ответы API не кэшируются service worker'ом (`NetworkOnly` для `/api/`), это правильно и не трогалось.

## Остаток кассы в строках `/api/devices` (исправлено на этапе 2)

`GET /api/devices` делает `include: { store: true }`, поэтому **каждый телефон в ответе несёт полную строку магазина, включая `cashBalanceUsd`**. Продавец и партнёр получают только телефоны своего магазина, то есть в сыром JSON видят остаток кассы своего магазина. Фронтенд из `store` использует только `store.name` (`mapDevice` в `src/api/mappers.ts`). Если продавцу не положено видеть остаток кассы, это утечка данных.
Исправление — `store: { select: { id: true, name: true, ... } }` — меняет контракт ответа, поэтому по условиям задачи здесь не сделано. Рекомендуется отдельной задачей.
