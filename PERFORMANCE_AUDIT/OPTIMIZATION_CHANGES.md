# Внесённые изменения

Ветка `perf/optimization` (от `main` @ `a459446`). Работа шла в два этапа:

- **Этап 1** — изменения без какого-либо изменения поведения.
- **Этап 2** — после того как владелец попросил исправить и оставшиеся пункты. Здесь две вещи видны пользователю или затрагивают схему, обе отмечены ⚠️:
  - история перемещений по умолчанию за 180 дней с кнопкой «показать старше»;
  - удалён дублирующий индекс БД.

## 1. Стабильные vendor-чанки (`vite.config.ts`)

`react-dom/client` (рендерер React), `scheduler`, `react-router` и `@capacitor/core` вынесены в отдельные vendor-чанки. Раньше рендерер попадал во входной чанк вместе с кодом приложения.

- Входной чанк: 273,2 → 87,4 КБ (gzip 84,8 → 26,5 КБ).
- После деплоя с изменённым кодом приложения на первой загрузке перекачивается 26,5 КБ вместо 84,8 КБ (gzip): React остаётся в кэше.

## 2. Docker-образ (`Dockerfile`)

После `npm prune --omit=dev` удаляются пакеты, которые серверу не нужны: react, lucide-react, exceljs, capacitor… и typescript. Сервер импортирует только `express`, `@prisma/client`, `ws`, `web-push`, `dotenv`; динамических импортов нет.

- Образ 722 → 573 МБ.
- `node_modules` 346 → 219 МБ.

Если серверный код начнёт импортировать пакет из этого списка, контейнер упадёт при старте с `Cannot find module`. Это сразу видно; правило записано в CLAUDE.md.

## 3. Панель кассы: `inventoryItems=0`

Панель показывает только итог склада. С параметром `inventoryItems=0` сервер не строит список всех телефонов, а итоги считает тем же кодом из тех же строк. Без параметра ответ байт в байт прежний.

- Ответ 446 497 → 12 157 Б.
- Время 39,9 → 19,1 мс (медиана A/B).

## 4. Строка магазина в списках

В `GET /api/devices`, `GET /api/sales`, `POST /api/sales` (ответ), `GET /api/repairs` и `PATCH /api/devices/:id` вместо `include: { store: true }` используется `store: { select: { id, name, isMainWarehouse } }`. Клиенты читают из `store` только `name`; серверный код эти поля тоже не использует (проверено поиском).

Побочный эффект: остаток кассы магазина (`cashBalanceUsd`) больше не повторяется в каждой строке. Продавец свой остаток видит и раньше через `/api/stores`, так что утечки не было, но и дублировать поле незачем.

Эффект (админ, все магазины):

| Ответ | До | После |
|---|---:|---:|
| `/devices` | 1 522 680 Б | 1 313 669 Б |
| `/sales?limit=500` | 816 700 Б | 754 200 Б |
| `/repairs?limit=500` | 237 013 Б | 222 013 Б |

## 5. Перемещения ⚠️

- **Сервер.** Позиции перемещения отдаются с полями `deviceId, imei, brand, model`: только их читает `mapTransfer`. Появился необязательный параметр `since` (ISO-дата): перемещения с `requestedAt ≥ since` плюс **все** ожидающие одобрения, какими бы старыми они ни были. На неверную дату — 400 «Неверная дата начала периода». Без параметра — вся история, как раньше.
- **Клиент.** По умолчанию загружаются последние 180 дней и все ожидающие. Внизу истории появилась кнопка **«Показать перемещения старше 180 дней»**: она загружает всю историю, после чего обновления в реальном времени тоже идут по всей истории. При выходе из аккаунта окно сбрасывается.
- **Эффект.** Полная история 901 919 → 498 143 Б только за счёт полей позиций. Окно дополнительно отсекает старое: в тесте с 8 из 24 перемещений старше 200 дней ответ 498 → 333 КБ. С годами разница растёт.

## 6. Отчёт: продажи и позиции двумя плоскими запросами (`reports.service.ts`)

Раньше позиции продаж загружались вложенной связью, и Prisma отправляла все id продаж периода обратно в `IN (…)` и сама склеивала строки. Теперь продажи и позиции читаются двумя параллельными плоскими запросами с одинаковым условием (`saleItem.where.sale = условие продаж`) и склеиваются по `saleId`. Порядок позиций прежний: у Prisma в обоих случаях нет ORDER BY.

- Загрузка продаж с позициями 187 → 79 мс.
- Отчёт ALL 443 → 327 мс.
- **Все 48 отчётов** (8 периодов × 6 вариантов магазина, с событиями) побайтно совпадают со старым кодом.

## 7. История продаж: одна раскладка

Для каждого чека рендерились две разметки сразу: таблица (компьютер) и карточка (телефон), одна из них скрыта CSS. Теперь рендерится только видимая: граница 768 px через уже существующий `useNavigationLayout`, тот же порог, что у Tailwind `md`. CSS-классы оставлены.

- DOM при месяце: 61 тыс. → 28–34 тыс. узлов.
- Полная отрисовка месяца на телефоне (CPU 4×): 6,9 → 5,4 с, самая длинная блокировка 4,7 → 2,7 с. С §13 итог — 2,9 с.

Также пробовался порционный рендер списка. Он **ухудшил** результат (телефон 7 → 14 с): каждая порция перерисовывала уже показанные строки. Поэтому его убрал (замер в BEFORE_AFTER_COMPARISON.md).

## 8. Версия сборки в `index.html`

`__COMMIT_SHA__` / `__BUILD_TIME__` / `__APP_VERSION__` больше не подставляются в JS. Плагин `version-json-plugin` пишет их в `<meta name="app-build">` в `index.html`, а `src/services/buildInfo.ts` читает их оттуда. Страница и её скрипты всегда из одной сборки, поэтому обнаружение обновлений PWA работает так же. `version.json` не менялся.

Константа менялась при каждой сборке, а через неё менялись входной чанк и имена всех чанков страниц. Теперь деплой без изменений фронтенда (например, исправление только на сервере) меняет **0** файлов ассетов вместо 49 (417 КБ gzip). Браузеры и service worker ничего заново не скачивают, кроме `index.html`.

В тесте `pwaUpdateService.test.ts` значение сборки теперь задаётся моком `buildInfo` (раньше vitest брал его из `define` конфига Vite).

## 9. Дублирующий индекс ⚠️

`@@index([imei])` удалён из `Device`; миграция `DROP INDEX IF EXISTS "devices_imei_idx"`. Уникальный индекс `devices_imei_key` на той же колонке остаётся, поэтому поиск по IMEI и уникальность не меняются. У дубля было 0 использований и в тестовой, и в локальной базе.

`prisma migrate diff` (миграции против схемы) после изменения показывает ровно те же расхождения, что и до него, и все они не по `devices` (см. REMAINING §3).

## 10. Сервер в проде — бандл вместо `tsx`

- `npm run build:server` собирает `server/src/index.ts` через esbuild в `server/dist/index.mjs` (ESM, пакеты внешние, source map).
- Dockerfile выполняет его после `npm run build`.
- `docker-entrypoint.sh` запускает `node --enable-source-maps server/dist/index.mjs`. Если бандла нет, запускается прежний `tsx server/src/index.ts`.
- CI тоже собирает бандл. `tsx` в образе остаётся для служебных скриптов.
- esbuild 0.25.12 уже стоял транзитивно через Vite; теперь он записан явной dev-зависимостью: +1 строка в `package.json` и lockfile.

Эффект:

- Старт сервера 742 → 401 мс (медиана 5 запусков).
- RSS в простое 114 → 89 МБ.
- В контейнере 1 процесс сервера вместо 3 (tsx, дочерний node и сервис esbuild).

## 12. Внешние ключи: схема приведена к базе

`prisma migrate diff` (миграции против схемы) показывал расхождения, которые были ещё до этой работы:

- ключ `owners_storeId_fkey` создан миграцией `20260930000000_partner_store_and_device_ram` (ON DELETE SET NULL), но в схеме связи не было. Следующий `prisma migrate dev` сгенерировал бы миграцию, **удаляющую** этот ключ;
- у `device_identifiers_device_id_fkey` и обоих ключей `payroll_payouts` в базе ON UPDATE NO ACTION, а схема по умолчанию подразумевала CASCADE.

Исправлена **схема**, а не база:

- в `Owner` добавлена связь `store` (`onDelete: SetNull, onUpdate: Cascade`), в `Store` — обратная `partnerOwners`;
- у трёх ключей указан `onUpdate: NoAction`.

Миграция не нужна, база и данные не меняются. После правки `prisma migrate diff` → «No difference detected».

Проверено на базе, развёрнутой с нуля миграциями, как прод. Локальная `mobile_shop_db` от миграций отличается (в ней нет `owners_storeId_fkey`): она создавалась иначе, и это не прод.

## 13. Форматтеры дат и сумм создаются один раз

Профиль переключения истории продаж на месяц (`scripts/sales-history-profile.ts`, привязка через source map) показал:

- `getBusinessDateKey` — 218 мс;
- `formatMoney` — 128 мс;
- форматирование времени и даты в строках.

Все они на каждом вызове создавали новый объект `Intl`.

Теперь `Intl.DateTimeFormat` / `Intl.NumberFormat` создаются один раз и переиспользуются. По спецификации ECMA-402 вывод тот же. Проверено: 200 тыс. сумм (3 локали × 4 точности) и 100 тыс. дат в Node и Chrome — **0 расхождений**. Скриншоты не изменились.

Месяц истории продаж:

- телефон 5,4 → 2,9 с;
- компьютер 1,14 → 0,83 с.
