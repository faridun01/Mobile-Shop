## 1. История продаж за месяц на телефоне

После исправлений (одна раскладка, форматтеры создаются один раз) месяц у админа по всем магазинам открывается так:

- компьютер — 0,83 с;
- телефон в эмуляции с замедлением CPU 4× — 2,9 с (было 6,9).

Оставшееся время — это в основном вёрстка браузера для ~28–34 тыс. DOM-узлов.

Продавец видит только свой магазин, примерно в 5 раз меньше чеков.

Дальнейшее ускорение возможно только изменением интерфейса. Варианты:

- **«Показать ещё»**: первые 100 чеков и кнопка. Просто и надёжно, но поиск Ctrl+F по странице находит только показанные.
- **Виртуализация**: в DOM только видимые строки. Самый быстрый вариант, но меняет прокрутку и печать страницы.

Порционный рендер без изменения интерфейса пробовался и ухудшил результат (см. BEFORE_AFTER_COMPARISON.md). Чтобы он работал, нужно вынести строку чека в мемоизированный компонент: это крупная переделка страницы на 1,7 тыс. строк.

## 2. Отчёт «за всё время»

После исправления 327 мс при 3,8 тыс. продаж (было 443). Отчёт читает все записи периода и считает деньги в `Decimal`, поэтому время растёт линейно с историей.

При ~15 тыс. продаж стоит перенести суммирование в SQL (`SUM` по `amountUsd` каждой записи — это соответствует правилу «каждая запись со своим курсом»). Затем сверить старый и новый отчёт до цента на копии реальных данных: скрипт `scripts/report-equivalence.ts` для этого уже есть.

## 3. Внешние ключи: схема против миграций — ✅ исправлено (OPTIMIZATION_CHANGES §12)

Схема приведена к ключам, которые создали миграции; база не менялась, `prisma migrate diff` пуст. Ниже — что было найдено.

Проверить, что на проде ключи такие же, как в миграциях (только чтение):

```bash
docker compose -f docker-compose.prod.yml exec db psql -U postgres -d mobile_shop_db -c "select conname, pg_get_constraintdef(oid) from pg_constraint where conname in ('owners_storeId_fkey','device_identifiers_device_id_fkey','payroll_payouts_employee_id_fkey','payroll_payouts_expense_id_fkey')"
```

Ожидается 4 строки; `owners_storeId_fkey … ON UPDATE CASCADE ON DELETE SET NULL`. Имена сервиса базы, пользователя и базы сверить с `docker-compose.prod.yml` на сервере.

### Найдено

`prisma migrate diff` (миграции против `schema.prisma`) показывает расхождения, которые были **до** этой работы:

```sql
ALTER TABLE "owners" DROP CONSTRAINT "owners_storeId_fkey";                       -- в схеме нет связи owners.store
ALTER TABLE "device_identifiers" DROP/ADD CONSTRAINT "device_identifiers_device_id_fkey" ... ON DELETE CASCADE ON UPDATE CASCADE;
ALTER TABLE "payroll_payouts"    DROP/ADD CONSTRAINT "payroll_payouts_employee_id_fkey"  ... ON DELETE RESTRICT ON UPDATE CASCADE;
ALTER TABLE "payroll_payouts"    DROP/ADD CONSTRAINT "payroll_payouts_expense_id_fkey"   ... ON DELETE RESTRICT ON UPDATE CASCADE;
```

**Риск (был).** Следующий `npx prisma migrate dev` добавит эти команды в новую миграцию. Внешний ключ `owners_storeId_fkey` будет **удалён**, а это ослабление целостности. Правила остальных ключей тоже изменятся.

Локальная `mobile_shop_db` разработчика от миграций отличается (нет `owners_storeId_fkey`, другие ON UPDATE). Это не прод, но при желании её стоит пересоздать миграциями.

## 4. `/devices` с историей телефона

Ответ 1,31 МБ (gzip ~90 КБ) на 1 571 телефон в наличии. Основной объём — сами телефоны и история каждого (`timeline`), которую показывает карточка телефона.

При десятках тысяч телефонов в наличии стоит загружать историю при открытии карточки, а не со списком. Это изменение поведения: карточка будет открываться с короткой загрузкой. Сейчас не приоритет.

## 5. Не проверено

- **iPhone / iOS Safari / установленное PWA / нативные сборки Capacitor не проверялись.** Все «телефонные» цифры — эмуляция в Chrome.
- Изменились раскладка чанков и источник версии сборки (мета-тег в `index.html`). Перед выкаткой стоит открыть приложение на одном iPhone и в установленном PWA и убедиться, что после деплоя появляется предложение обновиться.
- Применение миграции `20261016090000_drop_duplicate_device_imei_index` на проде не проверялось. Это одна команда `DROP INDEX IF EXISTS`, она выполнится автоматически при старте контейнера.
